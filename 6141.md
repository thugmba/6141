# Business Analytics and AI Application (Course 6141)

## Course Overview

Students in this course will develop a comprehensive understanding of business analytics and artificial intelligence fundamentals, covering topics such as business requirement analysis, data collection, and machine learning. Designed specifically for undergraduate and Master of Business Administration (MBA) students with zero prior programming background, this course emphasizes intuitive, evidence-based reasoning over abstract theoretical complexity.

Through hands-on exercises, students gain operational proficiency in Python programming, progressing from core syntax to intermediate techniques essential for enterprise data projects. Students acquire data manipulation skills using foundational libraries including NumPy and Pandas for data cleaning, aggregation, and financial visualization. They also master automated web data extraction techniques using HyperText Markup Language (HTML), Cascading Style Sheets (CSS), and Beautiful Soup to collect public competitor intelligence. 

With an introduction to modern machine learning tools through Scikit-Learn, participants learn to implement, interpret, and evaluate predictive models. Ethical considerations in artificial intelligence projects, algorithmic risk management, and governance frameworks are examined to ensure the responsible application of these analytical technologies.

* **Keywords (Core Programming Concepts):**
  * `Boolean Expression`: A logical comparison that evaluates strictly to `True` or `False`, used by computers to test commercial conditions (such as `annual_spend >= 50000.0`).
  * `Conditional Branching (else)`: Directing code execution down distinct logical pathways depending on operational thresholds, eliminating complex spreadsheet nested logic.
  * `List Collection`: An ordered, mutable sequence of business records enclosed in square brackets (e.g., `daily_orders = [120, 85, 94, 142]`), indexed sequentially starting from zero.
  * `Dictionary Collection`: A key-value associative data structure enclosed in curly braces (e.g., `{"client_id": "CUST-101", "annual_spend_USD": 145000.0}`), enabling instant data retrieval by descriptive business keys rather than numeric indices.
  * `Definite Iteration (for loop)`: A programmatic control structure that automatically iterates over every record in a collection, executing identical business rules across thousands of entries in milliseconds.

* **Core Programming & Computational Foundations:**
  * Eliminating Fragile Nested Spreadsheets: In Excel, multi-tier decision policies require nested formulas such as `=IF(C2>100000, "Platinum", IF(C2>50000, "Gold", IF(C2>20000, "Silver", "Standard")))`. These formulas quickly become unreadable, impossible to audit, and vulnerable to formula drift. In Python, conditional branching (`if-elif-else`) structures business rules into clean vertical indentation blocks that mirror managerial decision trees.
  * Deterministic Repetition over Human Fatigue: When processing transactional ledgers with thousands of rows, human analysts experience fatigue, eye strain, and copy-paste errors. A Python `for` loop executes repetitive calculations across 10 records or 1,000,000 records with identical mathematical precision and zero cognitive degradation.
  * Real-World Entity Modeling with Dictionaries: Modeling complex commercial entities as structured computational objects. A single customer account is captured as a dictionary of labeled attributes (name, industry, spend, risk score), while an enterprise client portfolio is structured as an iterable list of dictionaries.
  * Indentation as Syntax Structure (The Whitespace Discipline): Unlike older programming languages that use curly brackets `{}` or `BEGIN/END` tokens, Python enforces clean code formatting through whitespace indentation (4 spaces). An `IndentationError` occurs when code blocks are misaligned, serving as an automated guardrail for code readability.

* **1. Session Purpose:**

  * Our case: a retail chain exports monthly results for its 12 stores as a CSV file
  * Each row holds one store's sales, costs, visitors, and customer rating

* **2. Expected Learning Outcomes (By the end of this session, you will be able to):**

  2. "What is each store's profit margin?": create new columns with vectorized math (one formula runs on every row at once)
  3. "Which stores meet our target?": filter rows with `.loc[]` (keep rows that match a condition) and fix a `KeyError` (the column name does not exist)

* **3. Business Context: Why CSV?**
  * Where business data comes from: sales registers, the accounting system, the customer database, and Excel reports. Each system can export its tables as one shared file.
  * `.xlsx` (Excel file) vs `.csv` (CSV file):

    | | `.xlsx` Excel file | `.csv` CSV file |
    |---|---|---|
    | Format | Packed format | Plain text |
    | What you need to open it | A spreadsheet program such as Excel | Almost anything: Notepad, Excel, Google Sheets, Python `pandas`, AI assistants |
    | Opened in Notepad | Unreadable symbols (starts with `PK`) | Readable: `Store_ID,Region_Name,Monthly_Sales_USD` |

  * Trade-off: CSV keeps only values, with no formulas and no formatting.

* **4. Data Basics: Rows and Columns:**
  * **Row** (read across): one record. Here, all the facts about one store, such as row `1` = everything about `STR-1001`.
  * **Column** (read down): one type of information for every store, such as `Monthly_Sales_USD`. In pandas, one column is a `Series`.
  * **Cell:** one value where a row and a column meet, such as `185000.0`.
  * Size of a table: `df.shape` returns `(12, 6)` = 12 rows, 6 columns. Row labels (the `index`) start at `0`, not 1.

* **5. Lab Practice Dataset:**
  * File Link: [data/session_01_03_dataset.csv](data/session_01_03_dataset.csv)
  * Audited 12-row commercial store dataset used for vector arithmetic and filtering:
    * `Store_ID`: Unique retail location code (e.g., `STR-1001`).
    * `Region_Name`: Geographic division (East, West, North, South).
    * `Monthly_Sales_USD`: Gross store revenue in U.S. Dollars.
    * `Operating_Cost_USD`: Monthly operational store overhead in U.S. Dollars.
    * `Customer_Footfall_Count`: Total monthly foot traffic count.
    * `Customer_Satisfaction_Score`: Customer review rating (1.0 to 5.0 scale).

* **6. Keywords (Core Programming Concepts):**
  * `pandas` and `NumPy`:
    * What: free Python libraries for tables (`pandas`) and fast number arrays (`NumPy`)
    * Why: they sort, filter, and calculate tables of any size
  * `CSV file` and `pd.read_csv()`:
    * What: a plain-text table where commas separate values; `pd.read_csv()` loads it
    * Why: most business systems export data as CSV
  * `DataFrame`:
    * What: a whole table in Python, with row labels and column names
    * Why: it is the main object you clean, calculate, and filter
  * `Series`:
    * What: one column of a DataFrame, such as `df["Monthly_Sales_USD"]`
    * Why: most calculations work column by column
  * `Vectorized Computation`:
    * What: one formula applied to every row at once, with no loop
    * Why: fast, and nothing to drag down row by row
  * `.loc[]` vs `.iloc[]`:
    * What: `.loc[]` selects by label or condition; `.iloc[]` selects by position number
    * Why: pull out exactly the rows a question needs
    * Example: `df.loc[df["Region_Name"] == "West"]` keeps the West rows; `df.iloc[0:2]` keeps rows 0 and 1 (`0:2` starts at 0 and stops **before** 2)

* **7. Core Programming & Computational Foundations:**
  * **7.1 Columns, not cells: one formula for every row**
    * *The idea:* In Excel, a formula lives in one cell. To calculate the margin of 12 stores, you type the formula once and drag it down, which creates 12 separate copies, one per row. In pandas, a calculation is written once for a whole column, and pandas applies it to every row at the same time. This is called vectorized computation: the formula works on the whole column (a "vector" of values) instead of cell by cell.
    * *See it on real data:* operating margin for the first 3 stores.

      | | Excel | pandas |
      |---|---|---|
      | What you write | `=(C2-D2)/C2*100` in `E2`, then drag down to `E13` | `df["Operating_Margin_Pct"] = (df["Monthly_Sales_USD"] - df["Operating_Cost_USD"]) / df["Monthly_Sales_USD"] * 100` |
      | How many formulas exist | 12, one per row | 1, for the whole column |
      | `STR-1000` | `30.99` | `30.985915` |
      | `STR-1001` | `34.05` | `34.054054` |
      | `STR-1002` | `27.55` | `27.551020` |

    * *Common mistake (in Excel):* someone types a number over `E5`, for example to "fix" a value for a meeting. That row's formula is gone, the cell still looks normal, and next month's report is wrong without any warning sign that catches the eye. In pandas there is no per-row copy to overwrite: the next run recalculates every row from the data.
    * *More examples:*

      | Code | Result | What it tells you |
      |---|---|---|
      | `df["Monthly_Sales_USD"] - df["Operating_Cost_USD"]` | `44000.0` for `STR-1000` | operating profit for every store |
      | `df["Monthly_Sales_USD"] / df["Customer_Footfall_Count"]` | `11.45` for `STR-1000` | sales per visitor: what an average visitor spends |
      | `df["Operating_Cost_USD"] / df["Monthly_Sales_USD"] * 100` | `69.01` for `STR-1000` | cost as a share of sales, in percent |
      | `df["Monthly_Sales_USD"] * 1.05` | `149100.0` for `STR-1000` | a "what if sales grew 5%?" scenario |
      | `df["Monthly_Sales_USD"] / 1000` | `142.0` for `STR-1000` | sales in thousands, easier to read in a report |

    * *Remember:* write the rule once for the column; pandas applies it to every row.
  * **7.2 Inside a DataFrame: index, columns, and values**
    * *The idea:* A DataFrame has three parts, like a labeled spreadsheet:
      * the **index**: one label per row, shown at the left. By default the labels are `0, 1, 2, ...`, counting from `0`, not `1`;
      * the **columns**: one name per column, shown at the top, such as `Store_ID`;
      * the **values**: the data itself, stored as a NumPy array (a fast block of numbers that pandas uses underneath).
    * *See it on real data:* the first 3 rows as pandas prints them.

      ```text
         Store_ID Region_Name  Monthly_Sales_USD  ...
      0  STR-1000        East           142000.0  ...
      1  STR-1001        West           185000.0  ...
      2  STR-1002       North            98000.0  ...
      ```

      The `0`, `1`, `2` on the left are the index, not data. `STR-1001` is in the row labeled `1`, which is the **second** row.
    * *One column vs a smaller table:* `df["Store_ID"]` (single brackets) returns one column, a `Series`. `df[["Store_ID", "Region_Name"]]` (double brackets: a list inside the brackets) returns a smaller `DataFrame` with the listed columns.
    * *Common mistake:* counting rows from 1. In Python, the first row has position `0`, so "the third row" is position `2`.
    * *More examples:*

      | Code | Result | What it tells you |
      |---|---|---|
      | `type(df["Store_ID"])` | `Series` | single brackets give one column |
      | `df[["Store_ID", "Region_Name"]].shape` | `(12, 2)` | double brackets give a smaller table: 12 rows, 2 columns |
      | `df.columns.tolist()` | `['Store_ID', 'Region_Name', ...]` | the exact column names, to copy instead of typing |
      | `df.index.tolist()` | `[0, 1, 2, ..., 11]` | the row labels start at `0` |
      | `len(df)` | `12` | the number of rows |
      | `df.loc[0, "Store_ID"]` | `'STR-1000'` | one value: row label `0`, column `Store_ID` |

    * *Remember:* index on the left, column names on top, values in between; counting starts at `0`.
  * **7.3 Data types: every column has exactly one type**
    * *The idea:* pandas gives each column one data type (`dtype`), and every value in that column follows it. The type decides what you can do with the column: you can add numbers, but not text.

      | `dtype` | Meaning | Columns in our data |
      |---|---|---|
      | `float64` | decimal numbers | `Monthly_Sales_USD`, `Operating_Cost_USD`, `Customer_Satisfaction_Score` |
      | `int64` | whole numbers | `Customer_Footfall_Count` |
      | `str` | text (older pandas versions show `object`) | `Store_ID`, `Region_Name` |

    * *Why it matters:* if a number is typed with a comma, such as `"1,200"`, pandas cannot read it as a number, so the whole column becomes text. Adding text joins the pieces instead of summing them: a column with `"1,200"` and `"800"` "sums" to `"1,200800"`, not `2000`. In Excel the same value would sit in its cell as text and be quietly skipped by `SUM`.
    * *How to catch it:* run `df.dtypes` right after loading. A sales column showing `str` instead of `float64` means some values were stored as text.
    * *More examples:*

      | Code | Result | What it tells you |
      |---|---|---|
      | `df["Monthly_Sales_USD"].sum()` | `1829000.0` | a number column adds up as numbers |
      | `df["Region_Name"].head(3).sum()` | `'EastWestNorth'` | a text column "adds up" by joining the words |
      | `pd.Series(["1,200", "800"]).sum()` | `'1,200800'` | numbers stored as text are joined, not summed |
      | `pd.Series(["1,200", "800"]).str.replace(",", "").astype(float).sum()` | `2000.0` | remove the comma, convert to `float`, and the sum is right |
      | `df["Customer_Footfall_Count"].mean()` | `13075.0` | an `int64` column works for averages too |

    * *Remember:* check the types first; a number column must show `float64` or `int64`.
  * **7.4 Check before you calculate: four inspection tools**
    * *The idea:* A professional analyst never calculates on data they have not looked at. Four commands answer the first questions about any new file:

      | Command | Question it answers | Result for our file |
      |---|---|---|
      | `df.shape` | How big is the table? | `(12, 6)`: 12 rows, 6 columns |
      | `df.head(3)` | What do the first rows look like? | `STR-1000`, `STR-1001`, `STR-1002` |
      | `df.info()` | What are the types, and are values missing? | `12 non-null` in every column: no gaps |
      | `df.describe()` | What are the typical, smallest, and largest values? | sales: mean `152416.67`, min `89000.0`, max `225000.0` |

    * *Common mistake:* `df.shape` has no brackets, because it is a stored value (an attribute). `df.head()` and `df.info()` do have brackets, because they are actions (methods). Writing `df.shape()` raises `TypeError: 'tuple' object is not callable`.
    * *More examples:*

      | Code | Result | What it tells you |
      |---|---|---|
      | `df["Region_Name"].value_counts()` | `East 3`, `West 3`, `North 3`, `South 3` | how many stores each region has |
      | `df.isnull().sum().sum()` | `0` | the number of empty cells in the whole table |
      | `df["Customer_Satisfaction_Score"].min()` | `3.8` | the lowest rating |
      | `df["Customer_Satisfaction_Score"].max()` | `4.9` | the highest rating |
      | `df["Customer_Satisfaction_Score"].mean()` | `4.35` (rounded) | the average rating |

    * *Remember:* shape, head, info, describe: look first, calculate second.
  * **7.5 Picking rows: by label with `.loc[]`, by position with `.iloc[]`**
    * *The idea:* There are two ways to point at a row. `.loc[]` uses the **label** in the index, or a condition. `.iloc[]` uses the **position**, counting from `0`. On a freshly loaded file the labels and positions are the same, so the two look alike. They differ as soon as the rows are reordered.
    * *See it on real data:* sort the stores by sales, from lowest to highest. The row order changes, but every row keeps its label.

      | Request | Meaning | Result |
      |---|---|---|
      | `sorted_df.loc[1, "Store_ID"]` | the row whose label is `1` | `STR-1001`, wherever it now sits |
      | `sorted_df.iloc[0]["Store_ID"]` | whatever row is now first | `STR-1006`, the lowest sales |

    * *Filtering with `.loc[]`:* `.loc[]` also accepts a condition, such as `df.loc[df["Region_Name"] == "West"]`, and keeps only the rows where the condition is `True`. This is the form you will use most.
    * *Common mistake:* misspelling a column name. `df["Monthly_Sale_USD"]` (missing `s`) raises `KeyError: 'Monthly_Sale_USD'`: pandas looked for a column with that exact name and found none. Copy column names from `df.columns` instead of typing them.
    * *More examples:*

      | Code | Result | What it tells you |
      |---|---|---|
      | `df.loc[df["Region_Name"] == "East", "Store_ID"]` | `STR-1000`, `STR-1004`, `STR-1008` | the East stores: a condition plus one column |
      | `df.loc[df["Customer_Satisfaction_Score"] >= 4.5, "Store_ID"]` | `STR-1001`, `STR-1004`, `STR-1005`, `STR-1008`, `STR-1011` | the 5 best-rated stores |
      | `df.iloc[0]["Store_ID"]` | `'STR-1000'` | the first row |
      | `df.iloc[-1]["Store_ID"]` | `'STR-1011'` | `-1` means the last row |
      | `df.iloc[0:3]["Store_ID"]` | `STR-1000`, `STR-1001`, `STR-1002` | rows at positions 0, 1, 2 (stops before 3) |
      | `df.loc[2, "Region_Name"]` | `'North'` | row label `2`, column by name |
      | `df.iloc[2, 1]` | `'North'` | the same cell by position: row 2, column 1 |

    * *Remember:* `.loc[]` = label or condition; `.iloc[]` = position from `0`.

* **3. Business Context: Budget vs Actual:**
  * Four terms, one example (Consumer division, Q1):

    | Term | Meaning | Example |
    |---|---|---|
    | Budget | planned spending | `780,000` |
    | Actual | real spending | `810,000` |
    | Variance | Actual - Budget | `+30,000` |
    | Variance % | Variance / Budget x 100 | `+3.85%` |

  * Positive variance = overspent; negative variance = under budget.
  * Cost center: the accounting code a division's spending is charged to, such as `CC-202` for Consumer. Each cost center has a responsible VP (Vice President).
  * Company rule in our data: a quarter is flagged (`Audit_Status` = `Variance_Flag`) when the variance is more than 2%.
  * Consumer division by quarter: Q1 `+3.85%` (flagged), Q2 `+1.92%` (over, within the rule), Q3 `+5.77%` (flagged), Q4 `-0.64%` (under budget).

* **4. Data Basics: From Excel Tools You Know to pandas:**
  * Three Excel tools, in one line each:
    * **Filter:** hides the rows that do not match a rule, such as showing only the Consumer division.
    * **Pivot Table:** summarizes a large table by group. For example, put `Division_Name` in Rows and `Actual_Expense_USD` in Values to get total spending per division: 4 rows instead of 16.
    * **`VLOOKUP`:** a formula that looks up a value, such as a cost center code, in another table and returns a value from the same row, such as the VP's name. You tell it which column to return by number (for example, the 2nd column).
  * The same three jobs in pandas:
    * Filter -> Boolean mask `df[mask]`: the rule is written in code, so it repeats exactly next quarter.
    * Pivot Table -> `df.groupby().agg()`: one line; run it again when new data arrives.
    * `VLOOKUP` -> `pd.merge()`: `VLOOKUP` returns a column by number; `pd.merge()` matches rows by column name, such as `Cost_Center_Code`.

* **6. Keywords (Core Programming Concepts):**
  * `Boolean Mask`:
    * What: one `True` or `False` per row
    * Why: picks exactly the rows that meet a rule
  * `&` `|` `~`:
    * What: "and", "or", "not" for masks
    * Why: Python's `and` / `or` fail on whole columns
  * `Split-Apply-Combine`:
    * What: split rows into groups, calculate each group, combine the results
    * Why: the idea behind every pivot table
  * `groupby()` + `.agg()`:
    * What: `groupby()` splits; `.agg()` sums, counts, or averages each group
    * Why: yearly totals per division in one step
  * `pd.merge()`:
    * What: joins two tables row by row
    * Why: adds facts from another table, such as the VP's name, with no copy-paste
  * `Key Column`:
    * What: a column both tables share, such as `Cost_Center_Code`
    * Why: tells pandas which rows belong together

* **7. Core Programming & Computational Foundations:**
  * **7.1 Combining rules: `&`, not `and`**
    * *The idea:* A rule on a column, such as `df["Division_Name"] == "Consumer"`, does not give one answer. It gives one `True` or `False` **for every row**: a whole column of answers, called a Boolean mask. To combine two rules, Python must compare the two columns row by row: row 1 with row 1, row 2 with row 2, and so on. pandas uses `&` ("and"), `|` ("or"), and `~` ("not") for this row-by-row work.
    * *See it on real data:* the first 4 rows of our dataset.

      | Row | Division | `is_consumer` | `is_over` | Both true (`&`) | Either true (or) |
      |---|---|---|---|---|---|
      | `TXN-5000` | Cloud | `False` | `False` | `False` | `False` |
      | `TXN-5001` | Consumer | `True` | `True` | `True` | `True` |
      | `TXN-5002` | Enterprise | `False` | `False` | `False` | `False` |
      | `TXN-5003` | Logistics | `False` | `True` | `False` | `True` |

      Here `is_consumer = df["Division_Name"] == "Consumer"` and `is_over = df["Actual_Expense_USD"] > df["Budget_Expense_USD"]`. With `is_consumer & is_over`, a row is kept only when **both** columns say `True` (`TXN-5001`). With `is_consumer | is_over`, one `True` is enough (`TXN-5001` and `TXN-5003`).
    * *Common mistake 1, using `and`:* Python's own `and` can only judge one `True` or `False` at a time. Given a whole column, it does not know whether you mean "all rows", "any row", or "row by row", so it stops with `ValueError: The truth value of a Series is ambiguous`. "Ambiguous" means "it could mean several things".
    * *Common mistake 2, missing brackets:* Python works out `&` **before** `==` and `>`. So in `df["Division_Name"] == "Consumer" & df["Actual_Expense_USD"] > df["Budget_Expense_USD"]`, it first tries `"Consumer" & df["Actual_Expense_USD"]`, which makes no sense, and raises a `TypeError`. Brackets force the right order: `(df["Division_Name"] == "Consumer") & (df["Actual_Expense_USD"] > df["Budget_Expense_USD"])`.
    * In these examples, `is_over = df["Actual_Expense_USD"] > df["Budget_Expense_USD"]`.
    * *More examples:*

      | Code | Result | What it tells you |
      |---|---|---|
      | `(df["Division_Name"] == "Logistics") & is_over` | `Q1`, `Q3` | the Logistics quarters that overspent |
      | `(df["Fiscal_Quarter"] == "Q4") & is_over` | `Enterprise` | only one division overspent in Q4 |
      | `(df["Audit_Status"] == "Variance_Flag") & (df["Fiscal_Quarter"] == "Q3")` | `TXN-5008`, `TXN-5009`, `TXN-5011` | the flagged quarters in Q3 |
      | `(~is_over).sum()` | `8` | `~` flips the rule: 8 quarters stayed within budget |
      | `df["Division_Name"].isin(["Cloud", "Enterprise"]).sum()` | `8` | `.isin()` is a short way to write "Cloud or Enterprise" |

    * *Remember:* one rule gives one `True` / `False` per row; combine rules with `&`, `|`, or `~`, and put each rule in its own brackets.
  * **7.2 Split-apply-combine: how `groupby()` builds a summary**
    * *The idea:* Most management questions are about groups: "How much did **each division** spend?" Answering them always takes the same three steps, whether in an Excel pivot table or in pandas:
      1. **Split** the rows into groups, one per division.
      2. **Apply** a calculation inside each group, such as a sum.
      3. **Combine** the answers into a new, smaller table with one row per group.
    * *See it on real data:* the Consumer division's 4 quarterly rows go into one group, and `"sum"` adds them up:

      | Step | Consumer division |
      |---|---|
      | Split | Q1 `810000.0`, Q2 `795000.0`, Q3 `825000.0`, Q4 `775000.0` |
      | Apply (`"sum"`) | `810000.0 + 795000.0 + 825000.0 + 775000.0 = 3205000.0` |
      | Combine | one row: `Consumer` `3205000.0` |

      The same steps run for Cloud, Enterprise, and Logistics at the same time, so the 16 rows become 4: Cloud `1785000.0`, Consumer `3205000.0`, Enterprise `1280000.0`, Logistics `2468000.0`.
    * *What you choose:* the column to split by (`groupby("Division_Name")`), the column to calculate on, and the calculation: `"sum"` for totals, `"mean"` for averages, `"count"` for how many rows, `"max"` for the largest value.
    * *More examples:*

      | Code | Result | What it tells you |
      |---|---|---|
      | `df.groupby("Fiscal_Quarter")["Actual_Expense_USD"].sum()` | Q1 `2185000.0`, Q2 `2171000.0`, Q3 `2235000.0`, Q4 `2147000.0` | total spending per quarter: Q3 was the most expensive |
      | `df.groupby("Division_Name")["Transaction_ID"].count()` | `4` for each division | a quick check that no quarter is missing |
      | `df.groupby("Cost_Center_Code")["Actual_Expense_USD"].max()` | `CC-202` `825000.0` (largest) | the most expensive quarter of each cost center |
      | `df.groupby("Audit_Status")["Transaction_ID"].count()` | `Variance_Flag` `6`, `Verified` `10` | how many quarters were flagged |

    * *Remember:* `groupby()` does the split, `.agg()` does the apply, and pandas does the combine for you.
  * **7.3 Joining tables: match by name, not by position**
    * *The idea:* Information often sits in two tables: spending in one, the responsible VP in another. Joining means bringing the matching row from the second table next to each row of the first, using a column that both share: the key column, here `Cost_Center_Code`.
    * *Why Excel's `VLOOKUP` is fragile:* `VLOOKUP` is told to return "the 2nd column" of the lookup table. If someone later inserts a new column, such as `Region`, the 2nd column is now `Region`, and every formula quietly returns a region instead of a VP name. No error appears, so the mistake is easy to miss.
    * *Why `pd.merge()` is safer:* `pd.merge(spending, vp_info, on="Cost_Center_Code")` matches rows by the **name** of the key column and brings over every other column by name. Moving or inserting columns changes nothing.
    * In these examples, `ledger = pd.merge(df, vp_info, on="Cost_Center_Code", how="left")`, as in Micro-Example 3, and `vp_renamed` is `vp_info` with its key column renamed to `CostCenter`.
    * *More examples:*

      | Code | Result | What it tells you |
      |---|---|---|
      | `ledger.shape` | `(16, 8)` | still 16 rows; one new column, `VP_Lead`, added (7 + 1) |
      | `ledger.loc[ledger["Division_Name"] == "Logistics", "VP_Lead"]` | `David Kim` in all 4 rows | one VP row is matched to every quarter of that cost center |
      | `pd.merge(df, vp_renamed, on="Cost_Center_Code")` | `KeyError: 'Cost_Center_Code'` | `vp_renamed` calls the key `CostCenter`: the names must match exactly |

    * *Remember:* name the key column with `on=`; the key must have exactly the same name and the same values in both tables.
  * **7.4 What happens to rows with no match: `how="left"` vs `how="inner"`**
    * *The idea:* Sometimes a row in the main table has no partner in the other table, for example a new cost center that has not been given a VP yet. The `how=` setting decides what happens to that row.
    * *See it on an example:* suppose our spending table also had a new cost center, `CC-505`, which is not in `vp_info`:

      | `Cost_Center_Code` | `Variance_USD` | `VP_Lead` with `how="left"` | with `how="inner"` |
      |---|---|---|---|
      | `CC-202` | `85000.0` | Marcus Vance | Marcus Vance |
      | `CC-404` | `28000.0` | David Kim | David Kim |
      | `CC-505` | `5000.0` | `NaN` (empty) | row removed |

      `NaN` stands for "Not a Number", pandas' mark for a missing value.
    * *Why it matters:* with `how="inner"`, the `CC-505` overspend silently disappears from the report, and nobody is asked to explain it. With `how="left"`, the row stays and the empty `VP_Lead` tells you that someone must be assigned.
    * In these examples, `vp_3_rows` is `vp_info` without the `CC-404` row (as if Logistics had no VP yet), and `merged` is the result of the left merge.
    * *More examples:*

      | Code | Result | What it tells you |
      |---|---|---|
      | `pd.merge(df, vp_3_rows, on="Cost_Center_Code", how="left")` | `16` rows, `4` with `NaN` in `VP_Lead` | `vp_3_rows` lacks `CC-404`: its 4 quarters stay, with no VP |
      | `pd.merge(df, vp_3_rows, on="Cost_Center_Code", how="inner")` | `12` rows | the 4 Logistics quarters silently disappear |
      | `merged["VP_Lead"].isnull().sum()` | `4` | count the gaps after a left merge |

    * *Remember:* use `how="left"` when every row of your main table must stay in the report, then look for `NaN` to find the gaps.

  * `Ethical Scraping`:

* **7. Core Programming & Computational Foundations:**
  * **7.1 A web page is text with tags, not a table**
    * *The idea:* When you open a web page, your browser receives a long piece of text written in HTML and draws it as a page. The prices you see are inside that text, wrapped in tags such as `<span class="price">$49.50</span>`. A tag has three parts: an opening tag (`<span ...>`), the content (`$49.50`), and a closing tag (`</span>`). The `class="price"` part is a label that the website's designers put on the tag, and it is what we use to find it.
    * *See it on real data:* one product card from our saved BetaMart page.

      ```text
      <div class="product" data-sku="SKU-801">
        <h3 class="name">Office Desk Chair</h3>
        <span class="price">$49.50</span>
        <span class="stock">120 units</span>
      </div>
      ```

      | What we want | Where it is in the HTML |
      |---|---|
      | Product code | the `data-sku` setting of the `div` tag: `SKU-801` |
      | Name | inside the `h3` tag with class `name`: `Office Desk Chair` |
      | Price | inside the `span` tag with class `price`: `$49.50` |
      | Stock | inside the `span` tag with class `stock`: `120 units` |

    * *More examples:*

      | Code | Result | What it tells you |
      |---|---|---|
      | `<h3 class="name">Office Desk Chair</h3>` | tag `h3`, class `name`, content `Office Desk Chair` | the product name |
      | `<span class="stock">120 units</span>` | tag `span`, class `stock`, content `120 units` | the stock level, as text |
      | `<div class="product" data-sku="SKU-801">` | tag `div`, class `product`, setting `data-sku` | the card that holds one product; its code is a setting, not content |
      | `<h1>BetaMart Weekly Prices</h1>` | tag `h1`, no class, content `BetaMart Weekly Prices` | the page heading |

    * *Remember:* scraping means finding the right tags and taking the text inside them.
  * **7.2 Tags inside tags: the DOM tree**
    * *The idea:* Tags are nested: the `div` card contains the name, price, and stock tags, just as a folder contains files. This nesting is called the DOM tree (Document Object Model). Beautiful Soup reads the HTML text and builds this tree, so you can ask for "the price tag inside this card" instead of searching through raw text.
    * *Why nesting matters:* our page has 4 cards, and each one has its own price. If you search the whole page for `.price`, you get all 4 prices. If you first take one card and then search inside it, you get exactly that card's price, already paired with the right name.
    * *See it on real data:*

      | Search | Result |
      |---|---|
      | `soup.select(".price")` (whole page) | 4 tags: `$49.50`, `$320.00`, `$429.00`, `$195.00` |
      | `card.select_one(".price")` (one card) | 1 tag: `$49.50`, for `SKU-801` only |

    * *More examples:*

      | Code | Result | What it tells you |
      |---|---|---|
      | `soup.select(".stock")` | 3 tags: `120 units`, `38 units`, `15 units` | whole page: only 3, because one card has no stock tag |
      | `soup.select(".product")[1].find("h3").text` | `Wireless Router` | the name inside the second card (position `1`) |
      | `soup.select(".product")[3]["data-sku"]` | `SKU-810` | the code of the fourth card |
      | `soup.select_one(".product .stock").text` | `120 units` | a space in a selector means "inside": a stock tag inside a product card |

    * *Remember:* loop over the cards, then search inside each card; that keeps every value with its own product.
  * **7.3 Four ways to find tags**

    | Method | Finds | Returns | Example |
    |---|---|---|---|
    | `.find("h3")` | the first tag with that name | one tag | `Office Desk Chair` |
    | `.find_all("h3")` | every tag with that name | a list of tags | 4 product names |
    | `.select_one(".price")` | the first tag matching a CSS selector | one tag | `$49.50` |
    | `.select(".price")` | every tag matching a CSS selector | a list of tags | 4 prices |

    * *The idea:* `find` methods search by tag name; `select` methods use CSS selectors (Cascading Style Sheets), the same short addresses web designers use: `.price` means "class `price`", and `div.product` means "a `div` tag with class `product`".
    * *Getting the content:* a tag is not yet text. `.text` takes the words inside it (`"$49.50"`), and `tag["data-sku"]` reads a setting written inside the opening tag (`"SKU-801"`). `.strip()` removes spaces and line breaks around the text.
    * *More examples:*

      | Code | Result | What it tells you |
      |---|---|---|
      | `soup.find("span").text` | `$49.50` | the first `span` on the page happens to be a price |
      | `len(soup.find_all("span"))` | `7` | 4 price tags + 3 stock tags |
      | `len(soup.select("div.product"))` | `4` | the number of product cards |
      | `soup.select_one(".discount")` | `None` | no tag on the page has the class `discount` |
      | `soup.h1.text` | `BetaMart Weekly Prices` | a short way to get the first tag of a kind |

    * *Remember:* one tag: `find` / `select_one`; all tags: `find_all` / `select`; then `.text` for the words.
  * **7.4 Text is not a number yet**
    * *The idea:* Everything scraped is text, even prices. `"$49.50"` cannot be added or averaged. Two steps turn it into a number: remove the dollar sign with `.replace("$", "")`, which gives `"49.50"`, then convert it with `float()`, which gives `49.5`.
    * *Common mistake:* forgetting the conversion. Text "added" together is joined, not summed, and `float("$49.50")` with the `$` still there raises `ValueError: could not convert string to float`.
    * *More examples:*

      | Code | Result | What it tells you |
      |---|---|---|
      | `float("320.00")` | `320.0` | clean text converts directly |
      | `float("$1,299.99".replace("$", "").replace(",", ""))` | `1299.99` | remove every symbol first: the `$` and the thousands comma |
      | `int("120 units".split()[0])` | `120` | `.split()` cuts the text at spaces; `[0]` takes the first piece, `"120"` |
      | `"49.5" + "10"` | `'49.510'` | text is joined, not added |
      | `float("49.5") + 10` | `59.5` | after conversion, the math works |

    * *Remember:* clean the text first, then `float()`.
  * **7.5 Select by class name, not by position**
    * *The idea:* You could tell a script "take the 2nd tag in each card". That works until the website adds something, such as a red "SALE" badge before the price; then the 2nd tag is the badge and the script quietly collects the word "SALE". Selecting by class name (`.price`) follows the label, not the position, so it keeps working when the layout changes.
    * *More examples:* the same card before and after the website adds a "SALE" badge in front of the price.

      | Code | Before the badge | After the badge | What it tells you |
      |---|---|---|---|
      | `card.find_all("span")[0].text` | `$49.50` | `SALE` | "the first `span`" now points at the badge |
      | `card.select_one(".price").text` | `$49.50` | `$44.50` | the class name still finds the price |

    * *Remember:* use class names; still recheck the script whenever the site is redesigned, because class names can change too.
  * **7.6 When a tag is missing: `None`**
    * *The idea:* Real pages are irregular. On our page, the card for `SKU-807` has no stock tag. When `.select_one(".stock")` finds nothing, it returns `None`, Python's word for "nothing". Asking for the text of nothing, `None.text`, stops the script with `AttributeError: 'NoneType' object has no attribute 'text'`.
    * *The fix:* store the result first, check it, then read it:

      ```text
      stock_tag = card.select_one(".stock")
      if stock_tag is not None:
          stock = stock_tag.text.strip()
      else:
          stock = "not shown"
      ```

    * *More examples:*

      | Code | Result | What it tells you |
      |---|---|---|
      | `soup.select(".product")[2].select_one(".stock")` | `None` | the third card (`SKU-807`) has no stock tag |
      | `[c["data-sku"] for c in soup.select(".product") if c.select_one(".stock") is None]` | `['SKU-807']` | list every card with a missing stock tag |
      | `soup.select(".product")[0].select_one(".stock").text` | `120 units` | the first card has one, so `.text` works |

    * *Remember:* any tag might be missing; check for `None` before you read `.text`.

    * Why: shows what the data can answer, and where it looks strange
  * `Data Audit`:
    * What: the three checks: completeness, uniqueness, and validity
    * Why: one bad row can change a total by millions
  * `Baseline`:
    * What: today's value of the measure you care about
    * Why: the starting point for proving any later improvement
  * `assert`:
    * What: a line that stops the script with an `AssertionError` when a rule is broken, such as `assert (df["Contract_Value_USD"] > 0).all()`
    * Why: bad data is caught at the door, before it reaches a report
  * `try` / `except`:
    * What: runs code in `try`; if a chosen error happens, the code in `except` runs instead of stopping the script
    * Why: the script can report the problem clearly and keep going

* **7. Core Programming & Computational Foundations:**
  * Counting `True` values:
    * A condition on a column gives one `True` / `False` per row
    * `.sum()` counts the `True` values, because Python treats `True` as 1 and `False` as 0
    * `df.isnull().sum().sum()`: the first `.sum()` counts per column, the second adds the columns together
  * `.all()` and `.any()`:
    * `.all()` is `True` only if every value is `True`; `.any()` is `True` if at least one is
    * `assert (df["Contract_Value_USD"] > 0).all()` therefore means "every contract value is above zero"
  * `assert` with a message:
    * `assert rule, "message"` shows your message in the `AssertionError`, so the reader knows which rule failed
  * `try` / `except`:
    * Put the checks inside `try:`, and handle a failure under `except AssertionError as error:`
    * `error` holds the message, so you can print or save it

* **3. Business Context: How to Judge an AI Project:**
  * Every AI proposal is an investment: money now, savings later. Five numbers make proposals comparable (example: `AI-PRJ-101`, Supply Chain):

    | Term | Meaning | Example |
    |---|---|---|
    | Implementation cost | one-time cost to build the system | `150,000` |
    | Running cost | yearly cost to keep it working (cloud computing, updates); here 15% of the build cost | `22,500` |
    | Net annual benefit | yearly savings minus the running cost | `294,000 - 22,500 = 271,500` |
    | Payback period | months until the benefit repays the build cost: cost / net benefit x 12 | `6.6` months |
    | 3-year ROI | (net benefit x 3 - cost) / cost x 100 | `443.0`% |

  * Savings are forecasts, not facts. Two habits keep forecasts honest: include running costs, and compare every project with the same formula.
  * Labor hours saved are not the same as money saved: hours only become savings if the freed time is used for other valuable work.

* **4. Data Basics: AI, ML, DL, and When a Rule Is Enough:**
  * Three nested ideas:

    | Term | What it is | Business example |
    |---|---|---|
    | AI (Artificial Intelligence) | any computer system that does a task we link to human thinking | a chatbot answering customers |
    | ML (Machine Learning) | AI that **learns a rule from past examples** instead of being told the rule | flagging likely fraud from past fraud cases |
    | DL (Deep Learning) | ML with many-layered neural networks, for images, sound, and text | reading scanned invoices |

  * Rule or ML? Ask how stable and clear the decision is:
    * **Use a rule** when the policy is fixed and written down: "sales tax is 5% of the price". A rule is cheaper, exact, and easy to explain.
    * **Use ML** when the pattern is complex or changes over time, and you have many past examples with known outcomes: "which invoices look like fraud?"
  * ML makes a prediction; a person or a business rule still decides what to do with it.

  * `Machine Learning (ML)`:

  * `Payback Period`:

  * `ROI (Return on Investment)`:
    * What: total gain compared with the cost, in percent

* **7. Core Programming & Computational Foundations:**
  * Learning a rule from examples:
    * A rule-based system uses a number a person chose, such as "flag invoices above 250,000"
    * A learning system tries many candidate numbers on past examples, counts the mistakes, and keeps the number with the fewest mistakes
    * That search is the core idea of all machine learning; Session 3.3 uses a library that does it at scale
  * Two kinds of division by zero:
    * Plain Python numbers: `150000.0 / 0.0` stops the script with `ZeroDivisionError: float division by zero`
    * pandas columns: dividing by a `0` gives `inf` (infinity) with **no error**, and an `inf` ranks above every real value when you sort
    * Check before you divide: `if annual_benefit > 0:`
  * Budget allocation with a loop (a "greedy" method):
    * Sort projects by value per dollar, then go down the list and fund each project that still fits in the budget
    * Simple and fast, but not always the best combination (Exercise 3 checks this)

    past = pd.DataFrame({

                       300000, 330000, 410000, 450000, 520000],
        "Was_Fraud": [False] * 5 + [True] * 5,
    })

    rule_flags = past["Amount_USD"] > 250000

    for threshold in past["Amount_USD"]:

        mistakes = (flags != past["Was_Fraud"]).sum()
        if mistakes < best_mistakes:

* **4. Data Basics: From a Raw Row to a Model-Ready Row:**

    | Column | Raw value | Model-ready value | Step |

* **6. Keywords (Core Programming Concepts):**
  * `Features (X)` and `Target (y)`:
    * What: `X` holds the input columns; `y` holds the outcome to predict
    * Why: every Scikit-Learn model expects this split
  * `Imputation`:
    * What: filling missing values, for example with the column's median (the middle value)
    * Why: models cannot learn from rows with gaps
  * `One-Hot Encoding`:
    * What: one 0/1 column per text category
    * Why: turns text into numbers without inventing an order
  * `Standardization`:
    * What: rescaling a column to an average of 0 and a standard deviation of 1
    * Why: stops large-unit columns, such as income, from drowning out small ones
  * `Train/Test Split`:
    * What: keeping some rows aside to test the model at the end
    * Why: the only honest measure of how the model will do on new applicants
  * `Data Leakage`:
    * What: information from the test set slipping into training
    * Why: makes a model look better than it really is

* **7. Core Programming & Computational Foundations:**
  * Scikit-Learn (`sklearn`) tools work in two steps:
    * `.fit(train_data)` **learns** numbers from the data, such as a column's median or average
    * `.transform(data)` **applies** what was learned to any data, training or test
    * `.fit_transform(train_data)` does both in one call, for the training data only
  * The leakage rule: split first, then `fit` on the training set only, then `transform` both sets.
    * `scaler.fit_transform(X_test)` is the classic mistake: the scaler learns the test set's own average, so the test rows no longer show how different they are from the training rows
  * `train_test_split(X, y, test_size=0.25, random_state=42, stratify=y)`:
    * `test_size=0.25` keeps 25% of the rows (here 3 of 12) for testing
    * `random_state=42` fixes the random shuffle, so everyone gets the same split
    * `stratify=y` keeps the same share of defaults in both sets
  * Calling `.transform()` before `.fit()` raises `NotFittedError`: the tool has nothing learned to apply yet.

  * It has the sale records of 14 recent deals: size, number of rooms, distance to the city center, tax rate, and price
  * The valuation manager asks: can a model estimate a property's sale price from its size and location, and how far off will it be? Today, you train your first machine learning model and measure its error honestly

* **2. Expected Learning Outcomes (By the end of this session, you will be able to):**
  1. "Can a model learn prices from past deals?": train a linear regression model with Scikit-Learn's `.fit()` and read its coefficients (how much the price changes for one more unit of each feature)
  2. "How far off are the predictions?": measure the error with RMSE (Root Mean Squared Error) and MAE (Mean Absolute Error), and check stability with cross-validation (testing on several different splits)
  3. "What will this new building sell for?": predict the price of one new property, and fix the `ValueError` a one-row prediction often raises

* **3. Business Context: When a Price Model Is Worth Using:**
  * An estimate is useful if its typical error is small compared with the price. Our properties sell for about $513,000 on average, so a typical error of $10,000 (about 2%) is useful for a first quote, while a typical error of $100,000 would not be.
  * A model learns from past deals only. It should not be trusted far outside them, for example for a 10,000 square-foot tower when the largest past deal was 3,400 square feet.
  * Regression vs classification:
    * **Regression** predicts a number, such as a price. Today's model, linear regression, is one example.
    * **Classification** predicts a category, such as "fraud" or "not fraud". Logistic regression, used in Session 3.4, is one example.

* **4. Data Basics: How Linear Regression Works:**
  * Linear regression finds the best straight-line formula: `price = intercept + coefficient_1 x feature_1 + coefficient_2 x feature_2 + ...`. "Best" means the smallest total squared error on the training rows.
  * Reading a coefficient: the change in price for one more unit of that feature, **while the other features stay the same**. Example from Micro-Example 1: `+180.1` per square foot.
  * Coefficients can surprise you. On its own, distance rises with price (correlation `+0.98`), because the big buildings in our data are far from the center. Once size is in the model, each extra mile **lowers** the price by about $1,900: compared at the same size, a farther building is cheaper.
  * Three error measures, in plain words:

    | Measure | Meaning | Lower or higher is better? |
    |---|---|---|
    | MAE (Mean Absolute Error) | the average size of the errors, in dollars | lower |
    | RMSE (Root Mean Squared Error) | like MAE, but large errors count extra | lower |
    | R-squared | the share of the price differences the model explains, from 0 to 1 | higher |

* **6. Keywords (Core Programming Concepts):**
  * `Estimator` (`.fit()` / `.predict()`):
    * What: any Scikit-Learn model; `.fit(X, y)` learns from examples, `.predict(X)` makes predictions
    * Why: every model in the library uses the same two methods
  * `Linear Regression`:
    * What: a model that predicts a number with a straight-line formula
    * Why: simple, fast, and its coefficients are easy to explain to a manager
  * `Logistic Regression`:
    * What: a model that predicts the probability of a yes/no outcome
    * Why: the classification partner of linear regression (Session 3.4)
  * `RMSE` and `MAE`:
    * What: the typical prediction error, in the target's own unit (here, dollars)
    * Why: tells the manager how far off an estimate can be
  * `Cross-Validation`:
    * What: splitting the data into K parts and testing K times, each time on a different part
    * Why: one lucky split can make a model look better than it is
  * `Overfitting`:
    * What: a model that memorizes its training rows and does worse on new data
    * Why: the main risk when data is small; testing on unseen rows reveals it

* **7. Core Programming & Computational Foundations:**
  * The estimator pattern, in three lines:
    * `model = LinearRegression()` creates an empty model
    * `model.fit(X_train, y_train)` learns the coefficients

### Session 3.4: Core Concepts of Machine Learning: Supervised vs. Unsupervised Learning and Evaluation Metrics

![Session 3.4 Map](assets/session_03_04_map.png)

* **Lecture Presentation:** [Download Slides (PDF)](slides/session_03_04_lecture.pdf)
* **Reading (PDF):** [Download Reading (PDF)](handouts/session_03_04_reading.pdf): read before class
* **Schedule:** Week 12 (115/11/29 - 115/12/05) | In-person classes (1:2 Delivery Ratio: 60 Min Lecture + 120 Min Lab)

* **1. Session Purpose:**
  * A card issuer's fraud model gives every transaction a risk score from 1 to 100; above a cut-off score (the threshold), the transaction is held and the customer gets a verification text
  * The two possible mistakes have very different costs: a false alarm costs about $5 of checking, while a missed fraud costs the stolen money
  * The fraud operations manager asks: at what risk score should we stop a transaction, and what does each kind of mistake cost us? Today, you judge a model by business cost, not by a single accuracy number

* **2. Expected Learning Outcomes (By the end of this session, you will be able to):**
  1. "Which kind of learning fits this problem?": tell supervised learning (learning from examples with known answers) from unsupervised learning (finding groups without answers), and group transactions with K-Means
  2. "How good is the risk score, really?": read a confusion matrix (a 2x2 count of right and wrong decisions) and calculate precision, recall, and ROC-AUC
  3. "Where should we set the threshold?": choose the threshold with the lowest business cost, and fix the `ValueError` raised when scores are passed in place of 0/1 decisions

* **3. Business Context: Not All Mistakes Cost the Same:**
  * Every decision on a transaction lands in one of four boxes:

    | | Model says: fraud (hold it) | Model says: legitimate (let it pass) |
    |---|---|---|
    | **Really fraud** | TP (True Positive): fraud caught | FN (False Negative): fraud missed, the money is lost |
    | **Really legitimate** | FP (False Positive): false alarm, about $5 to check | TN (True Negative): normal purchase, no cost |

  * In our cost model, a missed fraud costs `$1,500` and a false alarm costs `$5`, so one miss costs as much as 300 false alarms.
  * The accuracy trap: if only 1% of transactions are fraud, a model that says "never fraud" is 99% accurate and catches nothing. Accuracy hides the costly mistakes.

* **4. Data Basics: Reading a Classifier's Report Card:**
  * Four measures, each answering one question:

    | Measure | Formula | Question it answers |
    |---|---|---|
    | Accuracy | (TP + TN) / all | What share of all decisions was right? |
    | Precision | TP / (TP + FP) | Of the transactions we held, what share was really fraud? |
    | Recall | TP / (TP + FN) | Of all the fraud, what share did we catch? |
    | ROC-AUC | area under the ROC curve, from 0.5 to 1.0 | How well does the score rank fraud above legitimate transactions, at every threshold? |

  * A higher threshold holds fewer transactions: fewer false alarms (higher precision) but more missed fraud (lower recall). The threshold moves this trade-off; the business cost decides where it should sit.
  * ROC-AUC (Area Under the Receiver Operating Characteristic Curve): `0.5` means the score ranks no better than a coin flip; `1.0` means every fraud scores above every legitimate transaction.
  * Supervised vs unsupervised:
    * **Supervised:** past examples come with the answer (`Actual_Fraud_Binary`), and the model learns to predict it. Today's risk score is a supervised model's output.
    * **Unsupervised:** no answer column; the method finds groups of similar rows by itself. K-Means is the most common example.

* **6. Keywords (Core Programming Concepts):**
  * `Supervised vs Unsupervised Learning`:
    * What: learning with known answers vs finding groups without answers
    * Why: the first question to ask about any ML project
  * `Threshold`:
    * What: the cut-off score above which the model's answer becomes "yes"
    * Why: the business sets it, not the model
  * `Confusion Matrix`:
    * What: the 2x2 count of TP, FP, FN, and TN
    * Why: shows each kind of mistake separately, so each can be priced
  * `Precision` and `Recall`:
    * What: the share of holds that were fraud, and the share of fraud that was held
    * Why: the two sides of the trade-off a threshold controls
  * `ROC-AUC`:
    * What: one number for how well a score ranks positives above negatives
    * Why: compares scoring models before any threshold is chosen
  * `K-Means Clustering`:
    * What: an unsupervised method that splits rows into K groups of similar values
    * Why: finds customer or transaction segments when no labels exist

* **7. Core Programming & Computational Foundations:**
  * From scores to decisions: `(df["Cardholder_Risk_Score"] >= 70).astype(int)` turns each score into `1` (hold) or `0` (pass). Metrics such as `confusion_matrix()` need these 0/1 decisions.
  * Passing the raw scores instead raises `ValueError: Classification metrics can't handle a mix of binary and continuous targets`: the answers are 0/1, but the scores are continuous numbers.
  * `confusion_matrix(y_true, y_pred).ravel()` flattens the 2x2 table into four numbers in the order `tn, fp, fn, tp`, so `tn, fp, fn, tp = ...` names them in one line.
  * `roc_auc_score(y_true, scores)` is the exception: it takes the scores themselves, because it checks every threshold at once.
  * K-Means needs scaled features (Session 3.2): otherwise the dollar amount, with its large numbers, would decide the groups on its own.

* **1. Session Purpose:**
  * A model that lives in an analyst's notebook creates no value; value comes only when its predictions trigger real actions, every day, without a person running the code
  * The card issuer from Session 3.4 wants its fraud model to score each night's transactions automatically and hold the risky ones
  * The head of operations asks: how do we put the fraud model to work every night, and how will we know when it starts to fail? Today, you save a trained model, reuse it on new data, and build the checks that warn you when the world changes

* **2. Expected Learning Outcomes (By the end of this session, you will be able to):**
  1. "How does a model get from training to daily use?": map an end-to-end decision system (data in, checks, model, action), and save and reload a model with `joblib`
  2. "Is new data still like the training data?": detect data drift (a change in the incoming data that makes a model less reliable) by comparing averages
  3. "What if something breaks at night?": monitor latency and accuracy from a run log, and handle a missing model file (`FileNotFoundError`) with a safe fallback

* **3. Business Context: From a Model to a Decision System:**
  * A decision system has four stages, run every night as one batch (a group of records processed together):

    | Stage | What happens | Example |
    |---|---|---|
    | Ingestion | collect the day's data | 120,000 card transactions |
    | Validation | check it before use | no missing values, all columns present |
    | Scoring | the model gives each record a probability | fraud probability from 0 to 1 |
    | Action | a business rule turns scores into actions | hold every transaction at 0.5 or above |

  * Batch vs real-time:
    * **Batch** scoring runs on a schedule, such as every night, for many records at once. It is cheaper, and fine when decisions can wait a few hours.
    * **Real-time** scoring answers one request within milliseconds, for example while a customer waits at the checkout. It is faster but costs more to build and run.
  * Models get worse over time, because customers and markets change. Two warning signs to watch:
    * **Data drift:** the new data no longer looks like the training data (for example, purchases are much larger in the holiday season)
    * **Performance decay:** accuracy on recent, checked cases falls

* **4. Data Basics: Saving a Model and Watching It:**
  * Training is slow and done rarely; scoring is fast and done often. So the trained model is **saved to a file** once, then **loaded** by the nightly job:
    * `joblib.dump(model, "models/fraud_model.joblib")` saves it
    * `joblib.load("models/fraud_model.joblib")` loads it back, ready to predict, with no retraining
  * A simple drift check compares each feature's average in the new batch with its average in the training data:
    * change in percent = (new average - training average) / training average x 100
    * Our rule: flag a feature when the change is more than 20% in either direction
  * A run log records every night's stages with their record counts and latency (how long a stage took, in milliseconds; 1,000 ms = 1 second). Rising latency or falling accuracy is an early warning.

* **6. Keywords (Core Programming Concepts):**
  * `End-to-End Decision System`:
    * What: ingestion, validation, scoring, and action joined into one automatic run
    * Why: turns predictions into business actions without manual steps
  * `Batch vs Real-Time Scoring`:
    * What: many records on a schedule vs one record on request
    * Why: the business deadline decides which one is worth its cost
  * `Model Persistence` (`joblib`):
    * What: saving a trained model to a file and loading it later
    * Why: train once, score every night
  * `Data Drift`:
    * What: new data that no longer looks like the training data
    * Why: a model is only reliable on data like the data it learned from
  * `Monitoring`:
    * What: tracking counts, latency, and accuracy for every run
    * Why: catches a failing system before customers do
  * `Fallback`:
    * What: a simple, safe rule used when the model is not available
    * Why: the business keeps running when something breaks

* **7. Core Programming & Computational Foundations:**
  * Folders for models:
    * `os.makedirs("models", exist_ok=True)` creates the `models` folder; `exist_ok=True` means "no error if it already exists"
    * `os.path.exists(path)` returns `True` if a file is there, so a script can check before loading
  * Probabilities instead of yes/no:
    * `model.predict_proba(X)` returns two columns per row: the probability of class `0` and of class `1`
    * `[:, 1]` takes the second column: here, the fraud probability
  * A `Pipeline` (from Session 3.2) saves the scaler and the model together, so the nightly job scales new data exactly as the training data was scaled.
  * Missing files: `joblib.load()` on a wrong path stops the script with `FileNotFoundError: [Errno 2] No such file or directory`. Check with `os.path.exists()` first, and switch to the fallback rule if the file is missing.

* **3. Business Context: Price, Volume, and Profit:**
  * A lower price sells more units but earns less on each one; a higher price earns more per unit but sells fewer. Profit depends on both:

    | Term | Meaning | Example (`PRD-200`) |
    |---|---|---|
    | Unit margin | price - unit cost | `$49.99 - $22.50 = $27.49` |
    | Gross margin % | unit margin / price x 100 | `55.0`% |
    | Daily gross profit | unit margin x daily units | `$27.49 x 32 = $879.68` |
    | Days of stock | inventory / daily units | `450 / 32 = 14.1` days |

  * Price elasticity of demand (PED): if elasticity is `-1.5`, a 1% price increase loses about 1.5% of units. When elasticity is between `0` and `-1`, customers barely react; below `-1`, they react strongly.
  * The goal is profit, not revenue: a cut can raise revenue and still lower profit, because each extra unit brings in less margin.
  * Seasonal stock: units left at the season's end lose most of their value. Our retailer sells leftovers to a liquidator (a company that buys surplus stock) for 40% of their unit cost, a loss of 60% of the cost on every unsold unit.

* **4. Data Basics: Measuring Elasticity with a Price Test:**
  * To measure how customers react, the retailer changed the price of `PRD-202` once a week for 5 weeks and recorded daily units sold:

    | Week | Price | Daily units |
    |---|---|---|
    | 1 | `$59.99` | `27.9` |
    | 3 | `$69.99` | `22.0` |
    | 5 | `$79.99` | `18.1` |

  * Elasticity is the slope of a straight line through `log(units)` against `log(price)`. A logarithm (log) turns percentage changes into differences, so the slope reads directly as "% change in units for a 1% change in price".
  * `np.polyfit(x, y, 1)` fits that straight line and returns its slope and intercept. Result: elasticity `-1.51`.
  * Using elasticity for a small price change: new units = old units x (1 + elasticity x price change). For `+5%`: `1 + (-1.51 x 0.05) = 0.9245`, so about 7.6% fewer units. This straight-line rule is an approximation that works for changes of up to about 20%.

* **6. Keywords (Core Programming Concepts):**

* **7. Core Programming & Computational Foundations:**
  * Logs and straight lines:
    * `np.log(column)` takes the natural logarithm of every value (NumPy works on whole columns, like pandas)

  * Simulating with a function: write the profit calculation once as `simulate(price_change)` and call it for every price change, so every scenario uses exactly the same formula.
  * Finding the best key in a dictionary: `max(results, key=results.get)` returns the key whose value is largest.

  * Before the model's annual review, the board's risk committee must confirm that it treats applicant groups fairly and that every rejection can be explained to the applicant
  * The chief risk officer asks: does our credit model treat applicant groups fairly, can we explain each rejection, and what should the board decide? Today, you audit the model for fairness, explain its decisions, and prepare the facts the board needs

* **2. Expected Learning Outcomes (By the end of this session, you will be able to):**

  2. "Why was this applicant rejected?": explain each decision with feature contributions (how much each feature pushed the score up or down)
  3. "What should the board decide?": compare one shared threshold's fairness and risk, write a governance record, and fix a `NameError` caused by a variable that only exists inside a function

* **3. Business Context: Fairness, Explanations, and Accountability:**
  * A model learns patterns from past data. If the past was unfair, for example because some groups had less access to credit, the model can repeat that unfairness at scale, without anyone intending it.
  * Two kinds of unfair treatment:
    * **Disparate treatment:** using a person's group directly in the decision, such as a different threshold for each group. In lending, this is prohibited in many countries, including under the US Equal Credit Opportunity Act (ECOA).
    * **Disparate impact:** a rule that treats everyone the same on paper, but approves one group far less often. It is a warning sign that must be investigated and justified.
  * The four-fifths rule: if one group's approval rate is less than 80% (four-fifths) of the most-approved group's rate, the gap needs review. It comes from US employment guidelines (1978) and is widely borrowed as a first screening test. Failing it is a reason to investigate, not proof of discrimination.
  * Explanations are required: US lenders must give rejected applicants the main reasons (an adverse action notice), and the EU AI Act (European Union Artificial Intelligence Act) treats credit scoring of people as high-risk, with duties for documentation, human oversight, and transparency.
  * Governance: the board stays accountable for automated decisions. It needs a written record of what was tested, what was found, and who decided what.

* **4. Data Basics: Three Fairness Numbers:**
  * Approval rate of a group = approved applicants in the group / all applicants in the group.
  * Disparate impact ratio = the lower group's approval rate / the higher group's approval rate. `1.0` means equal rates; below `0.80` fails the four-fifths rule.
  * Feature contribution (for a model that adds up features, like linear regression) = coefficient x (applicant's value - average value). A negative contribution pulled the score down. For such a model, this number is also the feature's SHAP value (SHapley Additive exPlanations, a widely used explanation method).
  * Our approval scores come from a model whose formula we were not given. We fit a linear regression that copies it from the scores (a surrogate model) and explain that copy. It reproduces the scores well (`R-squared` `0.975`), so its explanations are trustworthy for this model.

* **6. Keywords (Core Programming Concepts):**
  * `Disparate Impact`:
    * What: a rule that approves one group much less often than another, even though it never uses the group
    * Why: the most common way bias enters automated decisions
  * `Disparate Impact Ratio` and the `Four-Fifths Rule`:
    * What: the lower approval rate divided by the higher one, tested against `0.80`
    * Why: a simple, widely used first test of fairness
  * `Disparate Treatment`:
    * What: deciding differently because of a person's group
    * Why: prohibited in lending in many countries, so it can never be the fix
  * `Explainability` (feature contributions, SHAP):
    * What: showing how much each feature pushed a decision up or down
    * Why: applicants, regulators, and managers need reasons, not just scores
  * `Surrogate Model`:
    * What: a simple model fitted to copy a model whose formula is hidden
    * Why: makes a hidden model explainable, as long as the copy is accurate
  * `AI Governance`:
    * What: the rules, records, and people that keep AI decisions accountable
    * Why: the board, not the model, answers for the decisions

* **7. Core Programming & Computational Foundations:**
  * The average of a 0/1 column is the share of `1`s, so `df.groupby("Demographic_Group")["Approved"].mean()` gives each group's approval rate in one line.
  * Feature contributions for every applicant at once: `(df[features] - df[features].mean()) * model.coef_`. pandas subtracts each column's average and multiplies each column by its own coefficient.
  * `.idxmin(axis=1)` looks across the columns of each row and returns the column name with the smallest value, here the feature that pulled the score down the most.
  * Variable scope: a variable created inside a function exists only inside it. Using it outside raises `NameError: name 'ratio' is not defined`. To use a result outside, `return` it and store it: `ratio = approval_audit(df, 0.70)`.
